# 技术验证：JavaScript 算得够不够快（决策记录 D-004）

状态：**有结论：继续用 TypeScript（决策记录 D-016）**。云端和 iPhone 已测完；Mac Safari、Mac Chrome 还要跑一次确定性自检（2026-11-02）

## 测什么

D-004 定了用 TypeScript（编译成 JavaScript）写比赛核心，条件是：云端模拟一整场比赛不超过 1 秒，手机上不明显卡顿。否则比赛核心改用 Rust。

做法：写一个用完就扔的原型（`src/proto/sim.ts`），22 名球员按阵型跑动、传球、带球、抢断、射门，跑满 90 分钟，计时。

原型的「思考量」按正式引擎第一版大概会有的量估计，并且是在测之前定的，没有为了好看的数字去调：

- 每秒 20 步（固定步长），一场 108,000 步
- 无球球员每 0.25 秒想一次跑位：在 9 个候选点里比较，每个点都要算和全部 21 名其他球员的距离、传球线路有没有被挡
- 持球人每 0.1 秒想一次：评估传给每个队友（每条线路 6 个检查点 × 11 名对手能不能抢到）、8 个带球方向、射门
- 每步算每个人的朝向（用自己实现的反正切），每秒把全场状态记进校验码

## 结果：云端

机器：本次开发用的云端容器（Intel Xeon 2.1 GHz，Node 22）。

| 版本 | 一场用时 |
|---|---|
| **标准（上面的思考量）** | **约 0.7 秒** |
| 无球球员完全不思考 | 约 0.32 秒 |
| 持球人每 0.5 秒才想一次 | 约 0.69 秒 |
| 不算校验码 | 约 0.66 秒 |
| 每秒 10 步（思考频率不变） | 约 0.57 秒 |
| 思考频率加倍 | 约 1.07 秒 |

（每个数字是 3～5 次的中位数，同一台机器前后测会有 ±10% 的波动。复现：`npm run bench -- --variants`。）

- 同一个种子每次结果逐位相同；浏览器（Chromium）里算出的校验码和 Node 完全一样；Intel 和 AMD 两种处理器算出的也完全一样。
- 时间大头是无球跑位的计算（约一半），其次是所有人的移动（约两成），持球人的决策约一成半。
- 原型踢出来的比赛：比分 2:2，每队射门约 20 次、传球约 1300 次（太多，真实比赛约 500）、成功率约 90%（偏高）。原型不追求像足球，这些数字只说明它在做「足球该做的事」，计算量是真实的。

## 结论（云端部分）

**达标：0.7 秒 < 1 秒，继续用 TypeScript。** 但余量只有三成左右，所以给正式引擎定一条预算：

- 正式引擎的思考量要盯着测，每次重要改动后跑 `npm run bench`，自动检查也会把云端用时写进每次运行的摘要页。
- 如果以后接近 1 秒：先优化算法（例如只在局面变化时重新思考、只比较附近的对手），仍然不够再把最费时的部分改成 Rust（D-004 的备选方案）。
- AI 教练推演换人（阶段 2）需要在比赛中途快速模拟很多遍，不能用完整引擎硬算，要用简化的快速版本，这一点到阶段 2 再设计。

## 结论（2026-11-02）

- **D-004 维持，比赛核心继续用 TypeScript**（决策记录 D-016）。改用 Rust 的两个条件都没出现：云端一场 0.7 秒，不到 1 秒；iPhone 一场 0.39 秒，没有卡顿。
- **手机比云端测试机还快**：同一场比赛，iPhone 用的时间只有云端的一半多一点（0.39 秒对 0.7 秒）。所以在玩家的设备上直接算整场比赛是可行的；正式引擎的预算仍按最慢的云端算（1 秒以内），对玩家的设备是留足余量的。
- **确定性方案可行**：iPhone 的 Safari（苹果的 JavaScriptCore 引擎、ARM 处理器）和云端的 Node（谷歌的 V8 引擎、x86 处理器）是两套完全不同的引擎和硬件，算出的数学函数、随机数和整场比赛逐位相同。
- 还差 Mac Safari、Mac Chrome 的自检，用来完成阶段 0 检查点「确定性自检三个浏览器都通过」。它们不影响上面的结论。
