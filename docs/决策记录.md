# 决策记录

每条记录写清：决定了什么、为什么、什么情况下可以重新考虑。改决定时不删旧记录，新增一条说明。

### D-001 做足球经理，不做棒球经理（2026-10-29）

- **决定**：做足球经理模拟游戏。
- **理由**：足球市场大得多；FM 玩家对引擎和 AI 不满已久，有明确的空档。棒球经理已有 OOTP，玩家基数小。
- **代价**：竞争对手强，开发周期更长。

### D-002 定位：比赛真实，而不是功能更全（2026-10-29）

- **决定**：核心卖点是「没有神阵、对手会动脑子、换人算数」。不和 FM 拼数据库和功能数量。
- **理由**：一个人做不出比 FM 更全的游戏，只能在一点上比它好很多。这一点来自发起人自己作为 FM 玩家的不满。

### D-003 虚构世界加编辑器（2026-10-30）

- **决定**：国家和城市用真实的；联赛、球队、球员由程序生成，不用真实名字和队徽。提供编辑器和开放的数据格式，社区可以自己做真实名单补丁；官方不发布、不宣传补丁。
- **理由**：真实球员名字和队徽需要授权，个人拿不到。实况足球当年也是「假名加补丁」的模式。
- **风险**：全虚构会削弱代入感。靠编辑器、社区补丁和「自己带起来的球队」的养成感弥补。

### D-004 技术：TypeScript 网页技术（2026-10-31，待阶段 0 技术验证确认）

- **决定**：比赛核心、界面、2D 和 3D 画面全部用 TypeScript；3D 用 three.js；上 Steam 时用 Tauri 打包。
- **理由**：一种语言，浏览器里到处能跑，手机和 Mac 都能直接测；同一份核心代码在云端跑批量测试。
- **重新考虑的条件**：技术验证中，云端模拟一场完整比赛超过 1 秒，或手机上明显卡顿，则比赛核心改用 Rust 编译成 WebAssembly，其他部分不变。
- **曾考虑**：全用 Godot（编辑器操作多，发起人要自己学，脚本慢）；Rust 核心（更快但链条复杂）。

### D-005 比赛核心和画面完全分开（2026-10-30）

- **决定**：比赛核心只算「谁在哪、做了什么」，不依赖任何画面代码；2D 和 3D 都只是读取结果来演出。先做 2D，验证通过后再做 3D。
- **理由**：3D 不理想时可以单独换画面层，核心不用重写；先验证足球逻辑，再投入 3D。

### D-006 比赛必须可重现（2026-10-30）

- **决定**：同样的种子、阵容和操作，在任何设备上模拟出完全一样的比赛。比赛核心禁止使用 `Math.random`、系统时间和浏览器自带的三角、指数等函数，一律用项目自己的实现；按固定步长推进。
- **理由**：回放只需存种子和操作；反馈码能百分之百重现问题；神阵检测和 AI 推演结果可靠；为以后的联机留基础。这条以后补救基本等于重写，所以从第一行代码开始执行。

### D-007 先网页，后 Steam；不上国内商店（2026-10-30）

- **决定**：开发和公开试玩都用网页版；收费渠道是 Steam 抢先体验。
- **理由**：Steam 个人可以上架，不需要版号；国内应用商店和微信小游戏需要版号，个人拿不到。

### D-008 开发方式（2026-10-31）

- **决定**：Claude 在云端写代码、测试、部署；发起人在 Mac 和手机上试玩、反馈、做决定。每个任务开一个新会话；设计、决策和进度写在仓库里，不依赖聊天记录。到 3D 阶段再开启 Remote Control 连接发起人的 Mac。
- **理由**：会话太长会加载失败；仓库里的文档是每个新会话的起点。

### D-009 仓库公开（2026-10-31）

- **决定**：仓库 `football-sim` 设为公开。
- **理由**：发起人选择。免费，GitHub Pages 测试链接和自动化都能直接用。
- **代价**：代码和设计文档任何人都能看到。不要在仓库里放任何密钥或个人信息。

### D-010 3D 目标（2026-10-30）

- **决定**：3D 目标是接近 PS2 时代实况的观感；动作流畅度不承诺达到实况 8。2D 始终保留。
- **理由**：实况的动作是大团队加动作捕捉做出来的；经理游戏的核心是比赛逻辑。

### D-011 第三方资源许可（2026-10-30）

- **决定**：MIT、Apache、CC-BY 等宽松许可的代码、素材和数据可以使用，注明出处并记入 `docs/参考资料.md`。GPL、AGPL 项目只看思路，不复制代码。只限研究使用的数据（如 StatsBomb）只用于内部校准，不随游戏发布。

### D-012 确定性的具体做法（2026-10-31）

- **决定**：
  1. 比赛核心只通过 `src/core/math.ts` 使用数学函数。开平方、取整、绝对值、最大最小、32 位整数运算直接用浏览器自带的（IEEE 754 规定了这些的结果，各浏览器一定相同）；正弦、余弦、反正切、指数、对数、乘方由我们只用加减乘除自己实现。乘方运算符 `**` 也禁止。
  2. 随机数用 xoshiro128\*\*（作者放入公有领域的算法），种子用 splitmix32 展开；已和官方 C 参考实现逐个数核对。
  3. 校验码 64 位，浮点数按二进制位计入。
  4. 靠机器检查，不靠自觉：比赛核心有单独的类型检查配置，不认识任何浏览器和 Node 的接口；代码检查禁止核心里出现 Math、Date、Intl、计时器、异步、`**`、不带比较函数的 sort 等；数学函数、随机数、整场比赛都有「固定答案」测试。
- **理由**：D-006 的落地做法。自己实现的函数误差在最后一两位，游戏完全够用。
- **代价**：改动数学函数或随机数会让旧回放全部对不上，所以改之前要在这里新增一条说明。
- **重新考虑的条件**：某个浏览器的确定性自检不通过（例如开平方结果不同），就把出问题的函数也改成自己实现。

### D-013 开发工具（2026-10-31）

- **决定**：TypeScript 6.0、Vite 8 构建、Vitest 5 测试、ESLint 10 代码检查、Node 22 直接运行 TypeScript 脚本。比赛核心不依赖任何外部包。
- **理由**：主流、免费、许可证宽松（见参考资料）。没用刚发布的 TypeScript 7，因为代码检查工具 typescript-eslint 还不支持它。
- **重新考虑的条件**：typescript-eslint 支持 TypeScript 7 后升级（类型检查会快很多）。

### D-014 代码直接提交到 main（2026-10-31）

- **决定**：Claude 每次任务完成、本地全部检查通过后，直接提交并推送到 main，GitHub Actions 再自动跑一遍全部检查。不开 Pull Request。
- **理由**：发起人不审代码；每个新会话从 main 开始（D-008），工作必须在 main 上，新会话才看得到。
- **代价**：没有人工代码审查，质量靠自动检查和测试把关。
- **重新考虑的条件**：有第二个开发者加入，或发起人想逐次审核改动。

### D-015 测试链接的发布方式（2026-10-31）

- **决定**：长期用 GitHub Pages，自动检查通过后自动部署（D-009）。在那之前，测试链接发布在 claude.ai 上（只有发起人自己能打开）。
- **理由**：仓库目前实际是私有的（和 D-009 不一致），GitHub 免费账号的私有仓库不能用 Pages。claude.ai 链接让发起人马上能在 Mac 和手机上测试。

### D-016 技术验证结论：比赛核心继续用 TypeScript（2026-11-02）

- **决定**：D-004 维持，比赛核心用 TypeScript，不改 Rust。
- **依据**：技术验证原型（22 人跑满 90 分钟，见 `docs/技术验证.md`）在云端一场 0.7 秒，标准是 1 秒以内；发起人的 iPhone（Safari 26.6）一场 0.39 秒，第一次 0.52 秒，没有卡顿。D-004 写的两个改用 Rust 的条件都没出现。
- **附带结论**：
  1. 手机比云端测试机快，在玩家设备上直接算整场比赛可行。正式引擎的预算仍按最慢的云端算：一场 1 秒以内。
  2. iPhone 和云端算出的比赛逐位相同（两套不同的 JavaScript 引擎、两种不同的处理器），D-006、D-012 的确定性做法可行。
- **重新考虑的条件**：正式引擎在云端超过 1 秒，并且优化算法后仍降不下来，就把最费时的部分改成 Rust（同 D-004）。

### D-017 世界设定（设计问卷第 1 批，2026-11-02）

- **决定**（发起人全部按推荐，详见 `docs/问卷/1-世界设定.md`）：
  1. 第一个国家：英格兰，其他国家以后再加。
  2. 联赛：三级，每级 20 队，共 60 队，每个赛季 38 轮。
  3. 升降级：每两级之间 3 升 3 降，按排名直接升降。
  4. 杯赛：一个 60 队都参加的淘汰制杯赛。
  5. 日历：8 月开赛、次年 5 月结束，冬天不停赛，圣诞节前后赛程密集。
  6. 队名：真实城市名 + 常见后缀（城、联、竞技、流浪者等），排除所有真实存在的俱乐部名。阶段 3 生成世界时准备一张真实俱乐部名单，用来排除撞名。
  7. 球员国籍：本国球员约七成，其余来自其他国家。
  8. 开局：玩家任选一支球队。
  9. 中文界面里，球员名字显示原文。
- **理由**：目标玩家首先是 FM 老玩家，英格兰的联赛体系和赛程最有「足球经理」的味道；密集赛程让体能和轮换变得重要，正好体现「换人算数」。
- **重新考虑的条件**：阶段 3 做出这个世界后，发起人试玩觉得不对味。

### D-020 足球经理暂停，转向微信小游戏（2026-11-05）

- **决定**：发起人判断足球经理这条路最终走不通，转向做微信小游戏。足球经理**暂停**：代码、文档、测试链接都保留，不删除。问卷第 2 批和 `docs/预期和计划.md` 里的两个选择不再等回答。
- **理由**：发起人选择。参考 `docs/预期和计划.md`：上 Steam 的把握一成左右，要投入一年多。小游戏一款只要几天到几周，不火就换下一款，更适合一个人加 Claude 的规模。
- **更正 D-007**：「微信小游戏需要版号，个人拿不到」只对有内购（游戏里卖东西）的游戏成立。免费、只靠广告赚钱的小游戏，个人也能上线，但需要软件著作权登记（软著）和备案。这是第三方资料，正式操作前以微信官方文档为准。
- **规则不变**：做「同类型、有新点子」的原创游戏，不照搬任何现有游戏的名字、美术、关卡和代码（立项「明确不做」、CLAUDE.md「第三方资源」）。
- **重新考虑的条件**：发起人想重新捡起足球经理。
